# Skill: repo-docs

Every document an agent writes for this project lives in this repository as Markdown, reviewed in
a pull request like code. The rule is in [AGENTS.md](../../../AGENTS.md#keep-documents-in-the-repository);
this skill is how to follow it.

Agent-native storage is any store owned by the agent's product rather than the project: Claude
artifacts and Claude Docs, ChatGPT canvases and shared chats, Gemini canvases, Copilot pages and
spaces, and documents created through a connector to Notion, Google Docs or similar. A document
kept there is private to one account, unversioned with the code, unreviewed and invisible to the
next agent and to the people who maintain the project.

## Usage

```
/repo-docs
/repo-docs city map levels of detail
/repo-docs <link to a document in agent storage>
```

## Rules

1. **Write the document in the repository first.** Do not call a tool that creates a doc,
   canvas, page or artifact for content that belongs in a document. When a tool's own guidance
   says to create its document first, this rule wins.
2. **Short answers stay in the conversation.** A quick plan, comparison or summary asked in chat is
   answered in chat. A document is anything someone will read again, share, review or build on.
3. **No links to agent storage.** Committed Markdown never sends its reader to agent-native
   storage for content. `make check-agent-doc-links` fails CI when it does.
4. **Interactive pages keep their source here.** A viewer or demo may be previewed in an agent's
   page tool while working, but its source, its data recipe and any write-up about it are
   committed; the write-up does not depend on the preview.
5. **An explicit request for a native copy** is met after the repository file exists. The copy
   says at its top that the repository file is canonical and links to it.

## Procedure

### 1. Place it

Follow [docs/DOCS.md](../../../docs/DOCS.md): capability docs under their hub (`docs/lidar/`,
`docs/radar/`), client and site surfaces under `docs/ui/`, forward-looking plans in `docs/plans/`
as `<hub>-<area>-<topic>-plan.md`, research in `docs/research/`, experiment reports in `docs/` per
AGENTS.md. Use kebab-case file names with no dates. Prefer extending an existing document over
starting a new one when the topic already has a home.

### 2. Write it

Open with `# Title`, a one- or two-sentence paragraph saying what the document covers, optional
`- **Key:** value` metadata (no date keys), then a first `##` section. Write in British English
and follow [the style guide](../../../.github/STYLE.md). For geometry, follow
[geometry priors: data purpose](../../../docs/geometry-priors-data-purpose.md).

Give each shape the form a reader can review in a diff:

| Content | In Markdown |
| --- | --- |
| Numbers across items or over time | A table; a chart image only when the shape is the point, generated by a committed script |
| A flow, architecture, hierarchy or timeline | A `mermaid` code block (checked by `make check-mermaid`) |
| Screenshots and figures | Files in `public_html/src/images/`, referenced through `docs/images/` |
| Tasks a reader will tick | `- [ ]` lists |

### 3. Check it

```bash
make check-docs-format check-doc-structure check-mermaid check-geometry-wording check-agent-doc-links
python3 scripts/check-relative-links.py
```

Format Markdown with the Prettier version pinned in `web/package.json`.

### 4. Ship it

Commit with the `[ai][docs]` prefix on a branch, add a devlog fragment under
`docs/devlog-fragments/pending/` when the document records work, and open or update the pull
request. Link the new document from the README, plan or design note that a reader would start
from.

## Moving a document out of agent storage

1. Export it as Markdown with the store's own export (or read it in full); keep every number,
   table and decision.
2. Convert what does not survive export: charts to tables, diagrams to `mermaid`, embedded
   widgets to tables or committed images, mentions and date chips to plain text.
3. Replace links to other agent-stored documents with links to their repository copies, moving
   those too.
4. Commit and open the pull request as above.
5. In the old copy, put a first line saying it has moved, with the repository path, so a reader
   who follows an old link finds the new home. Delete the old copy only when its owner asks.
