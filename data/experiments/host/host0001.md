# host0001: what each role costs on the Pi 5 and the Mac

**Question.** The binary links every role for every role: `velocity jobs` needs no internal
package and ships with libpcap, Typst, gRPC and tailsql, and the build always carries the `pcap`
tag. The review proposes to keep one binary and make each role a composition root with a closure
that CI asserts. What this does not say is whether a role-scoped build would also be worth
shipping: on the Pi, the deployment target, how much of the binary's size, start time and
resident memory is paid for roles the Pi never runs, and would a hub or a client built without
cgo be smaller or faster by an amount anyone would notice.

**Arms.** `one` is the shipped static build. `notypst` is the same build without the embedded
Typst engine, which the size plan puts at about 30 MB on ARM64. `nopcap` drops the `pcap` tag and
the L1 network package, which is what a hub or a client needs. `worker` links the worker applet
alone. Every arm runs `config/tuning.defaults.json`; the arms differ in what is compiled, never
in what is configured.

**Measures.** Binary size on disk; time from exec to `/api/version` answering; resident memory at
idle after 60 s; for the arms that replay kirk0, the full profile's frame-time p95 and peak
resident memory, three repeats on the Mac and one on the Pi 5.

**Rule, written before the builds (2026-10-19).** One binary stays the shipped artefact unless
the edge build (`one` against `notypst` tells the Typst share, `one` against `worker` tells the
rest) is at least a quarter smaller and idles in at least a sixth less memory on the Pi 5; frame
time is not expected to move and a move either way is reported, not scored. Whatever the numbers,
the closure test is adopted: it costs nothing at run time and is what keeps the roles real. If the
`nopcap` build starts faster or idles smaller by the same margins, it becomes the build a Mac
cross-compiles for a hub on the NAS, and still does not ship to the Pi.

**What could mislead.** The linker may already drop unreferenced embed data, so `notypst` could
show a smaller difference than the size plan predicts; the report says what the linker kept.
Resident memory at idle depends on what the server opens at start (the web embed, the docs
embed, the SQLite pool), not on what is linked; the report separates the two by measuring after
60 s with no request served.

**What it does not establish.** Nothing about CPU under live ingest: kirk0 is a replay. Nothing
about the worker's reproducibility, which is host0002 and host0003.
