# host0004: a pure-Go capture reader against libpcap

**Question.** Every production use of libpcap opens a capture file (`pcap.OpenOffline`, five
call sites) and filters it to one UDP port; the server's self-check only proves libpcap loads.
The repository already reads pcap and pcapng in pure Go through `gopacket/pcapgo`. If the pure-Go
reader returns the same packets at the same speed, the binary needs no cgo: every role builds
with `CGO_ENABLED=0`, a Mac cross-compiles a Pi or NAS binary without Docker, and the zig, musl
and vendored libpcap toolchain of D-26 can retire. Does it?

**Arms.** `libpcap`, the shipped reader; `purego`, the `pcapgo` reader with the port filter on
the decoded UDP layer. Both run the defaults; they differ in how packets are read, never in what
is configured.

**Measures.** Per case: packet count, and each packet's capture timestamp and payload digest, from
both readers; then frames and track rows from a replay of each; read wall time and replay wall
time, three repeats on the Mac; on the Pi 5, read wall time, frame-time p95 and peak resident
memory.

**Rule, written before the runs (2026-10-20).** The pure-Go reader replaces libpcap when, on all
four cases:

1. both readers yield the same packets in the same order, with identical capture timestamps to
   the nanosecond and identical payload digests;
2. replays under each reader give identical frames and identical track rows;
3. the pure-Go read is no more than 5 % slower than libpcap's on the Mac's median of three, and no
   more than 10 % slower on the Pi 5.

If clause 1 fails, the report names the first differing packet and why (link type, truncation,
timestamp resolution) and libpcap stays. If only clause 3 fails, the pure-Go reader still ships
for the hub and client builds, which never read captures in bulk, and the edge keeps libpcap. If
all three pass, D-26 is restated for a binary built without cgo, and the static Docker build and
the vendored libpcap retire in one release.

**What could mislead.** The real-time reader sleeps between packets, so its wall time says
nothing about read cost: the timing clauses read in analysis mode only. A capture with packets
on other ports or other protocols exercises the filter; kirk0 alone may not, so the corpus cases
are chosen to include one recorded with forwarding on.

**What it does not establish.** Nothing about live ingest, which reads UDP sockets and uses
neither reader. Nothing about captures from sensors other than the Pandar40P.
