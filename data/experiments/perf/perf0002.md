# perf0002: which replay speed a published scene should use, and whether analysis mode loses anything

**Question.** Published scenes are replayed at half speed (`REPLAY_SPEED_MODE=scaled`,
`REPLAY_SPEED_RATIO=0.5`), which costs a 24-site batch about 18 hours. Analysis mode replays as
fast as the pipeline takes packets, blocks rather than drops frames, and is exempt from the replay
frame-rate throttle, so it is meant to record every frame and lose nothing. Is it, and if it is,
should scenes use it? If paced replay stays, is 0.5x the right ratio or an arbitrary one?

## What the code says today

The reason 0.5x was chosen is recorded in `publish-scenes.py`: one capture gave 2.0 clusters per
frame in analysis mode against 16.8 at half speed and a VRLOG holding 23 % of its frames,
attributed to the background warm-up being gated on wall clock, and "every rate from 0.5x down
scores the same". Reading the code as of `0504248c`, three things have moved since or were not
part of that account:

1. **Warm-up runs on capture time.** The pipeline passes `frame.StartTimestamp` to
   `ProcessFramePolarWithMaskAt`, so `warmup_duration_nanos` (30 s) and `freeze_duration` (5 s)
   are measured in capture time. Only `SettlingStatus`, a report, still reads the wall clock.
2. **Paced replays run different L3 settings.** The scaled and realtime path in
   `startPCAPLockedWithConfig` replaces five L3 parameters for the replay: closeness 2.0 (the
   tuning file says 3), safety margin 0.30 m (0.15), neighbour confirmation 5 (3), seed from first
   observation and noise relative 0.02 (unchanged). Analysis mode uses the tuning file as written.
   The 2.0-against-16.8 comparison compared two L3 configurations as much as two speeds, and every
   0.5x scene published records a `tuning_hash` for settings its L3 did not run.
3. **Paced replays above 2.5x are thinned.** Non-analysis replays skip L4 to L6 on frames
   arriving faster than `MaxFrameRate` (25 fps) and record them empty. At 10 Hz that starts above
   a ratio of 2.5, so x4 is expected to record empty frames; analysis mode is exempt.

The frame builder still times its buffer timeout and cleanup on arrival time, which differs
between paced and unpaced replay. Whether that changes what is recorded is part of the question.

## Before the replays (2026-10-18)

Two corrections to the account above, written before any replay ran:

- **The throttle does not apply to these arms.** It is skipped whenever the replay preserves its
  grid (`analysis_mode: true`, `PipelineState.AnalysisMode`), not only in the analysis speed mode,
  and `publish-scenes.py` sends `analysis_mode: true` at every speed. Every arm here does the same,
  as published scenes do, so x4 is not expected to record empty frames; x2 against x4 then tests
  pacing alone. The frame accounting still counts empty frames, so the expectation is checked.
- **The cases are the published corpus's trimmed captures**, the files `publish-scenes.py` replays
  (`sf-street-speeds/raw/lidar/`, 1,227 s, 955 s and 2,033 s), staged on the internal disk so
  every arm reads the same bytes from the same disk and analysis-mode wall times are not bound by
  the USB volume. VRLOGs are written to the LiDAR volume, never to the disk the capture is read
  from.

Paced arms run up to four at a time, each on its own server: a paced replay's wall time is set by
the ratio, and the frame accounting shows whether one fell behind. The analysis arms run alone,
with nothing else on the host, since their wall time is a measurement.

## Arms

Each pair below differs in one thing:

| Pair                                 | Isolates                                |
| ------------------------------------ | --------------------------------------- |
| x0.5 against x0.5-replay-l3          | the L3 override, at the published speed |
| analysis against analysis-replay-l3  | the L3 override, unpaced                |
| analysis against x0.25, x0.5, x1, x2 | pacing, on the tuning file's own L3     |
| x2 against x4                        | the frame-rate throttle                 |

`x0.5-replay-l3` is today's published configuration; it is the reference for "does a change keep
the scenes as they are". The other paced arms use the override switch to run the tuning file's L3.

## Metrics, per arm per case

1. **Frames.** PCAP rotations, VRLOG frames, frames recorded empty by the throttle, frames the
   frame builder dropped (`[PCAP quality]`), and frames whose L4 was suppressed. Analysis mode's
   claim is that the first two are equal and the other three are zero.
2. **Content.** Foreground points and clusters per frame; confirmed tracks; track rows; median
   and p90 track life; the frame the L3 grid settles on.
3. **Determinism.** For the two repeated arms, whether the second replay's tracks match the first
   row for row (positions, velocities, boxes, a one-to-one identity map), as the 0.5x rerun of
   ashbury-downey did against the September recording.
4. **The scene.** The exported scene compared field by field with x0.5-replay-l3's, by the
   comparison used to check the October 17 rerun.
5. **Cost.** Wall time per replay.

## The rule, written before the replays

Analysis mode is adopted for scene publishing if all of these hold on every case:

- VRLOG frames equal PCAP rotations, with zero throttled, dropped or suppressed frames, in both
  repeats.
- Its two repeats agree row for row.
- Against x0.25 (the slowest, taken as the reference for pacing), clusters per frame, confirmed
  tracks and track rows are within 2 %.
- It takes at most a quarter of x0.5's wall time.

If analysis passes the first two and fails the third, pacing still matters, and the scene speed is
the fastest paced ratio whose content is within 2 % of x0.25's on every case. 0.5x keeps its place
only if nothing faster qualifies.

The L3 override is answered separately: whether published scenes should keep it is a tuning
decision (closeness 2 against 3 moves foreground a long way) and goes to an `l3bg` spec, not
here. Until then a scene's provenance should record the override it ran.

## What could mislead

- **One quiet site.** ashbury-downey, embarcadero-bay and columbus-broadway span a quiet
  residential corner, the shortest stretch and a busy one. A difference on only one of them is
  reported as such, not averaged away.
- **A loaded host.** Paced arms are insensitive to it until the pipeline falls behind, and the
  frame accounting shows if it did. Run nothing else on the worker: analysis-mode wall times are
  the one measurement that depends on it.
- **Equal is not right.** Agreement between arms says the speed does not matter. It does not say
  any arm's tracks are correct: none of these sites is labelled. A follow-up on kirk0's reviewed
  poses would be the check of that.
