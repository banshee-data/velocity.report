# perf0003: analysis mode for published scenes, asked again

**Question.** perf0002 asked whether analysis mode records what a paced replay records and loses
nothing, and could not answer it: its arms ran several replays per server, and the server carried
L3 state from one replay to the next (l3bg0020, l3bg0021). On the eight replays it ran on new
processes, analysis mode, 0.25x and 2x were identical row for row. With l3bg0021's reset in place,
the question is asked as perf0002 meant to ask it, on one server without restarts.

**Arms.** Analysis mode, 0.25x and 0.5x, every one on the tuning file's own L3
(`keep_tuning_l3`), so the comparison is pacing alone. The published configuration's substituted
L3 is a tuning question (`l3bg`), not this one's.

**Rule, written before the replays (2026-10-18).** Analysis mode is adopted for scene publishing
(`SCENE_SPEED_MODE=analysis` in the Makefile and `publish-scenes.py`) when, on every case:

1. VRLOG frames equal the capture's rotations, with no frame throttled or dropped, in both
   analysis repeats;
2. the two analysis repeats are identical row for row;
3. analysis is identical row for row to x0.25 and to x0.5 over the frames they share (perf0002's
   2 % was written for an effect that turned out not to exist; a paced replay that keeps its pace
   should now match exactly, and one that falls behind is reported with its lag);
4. analysis takes at most a quarter of x0.5's wall time.

If clause 3 fails on a paced replay that kept its pace, pacing changes what is recorded after all,
and the report says from which frame; 0.5x then stays. Republishing the existing scenes under the
new speed is a separate, outward-facing decision: this experiment changes the default for the next
batch and says what a republish would change.
