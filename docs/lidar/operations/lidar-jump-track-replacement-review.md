# Jump-track replacement review

- **Status:** Reviewed and frozen
- **Scope:** Production database (`sensor_data.db`), all tracks with lifetime peak speed ≥ 6 m/s
- **Answers:** Q8 in [lidar-state-estimation-plan.md](../../plans/lidar-state-estimation-plan.md#21-open-questions-and-experiments-needed) — "Do replacement jump candidates represent the same phenomenon?"
- **Frozen artefact:** [lidar-jump-track-replacement-20260915.json](lidar-jump-track-replacement-20260915.json), SHA-256 `21b2e500400150ee4185fa30386a4c70697d8fb179699a174f620415dedf6647`
- **Related:** [State estimation](../../plans/lidar-state-estimation-plan.md) Section 1.5 (extractor description), [Phase 0/1 corpus baseline](state-estimation-phase01-corpus-baseline.md)

## Background

The original 33-track jump regression set is unavailable — neither the row list nor the database
snapshot that produced it survives. [`lidar-jump-candidates.py`](../../../scripts/lidar-jump-candidates.py)
is the replacement extractor: a five-point time-domain XY line fit centred on each observation,
screening for a lateral residual above 0.5 m on tracks with lifetime peak speed ≥ 6 m/s and local
fit speed ≥ 2 m/s, with a 0.3 s max gap between observations. It is deliberately a reproducible
_review queue_, not ground truth: every output row starts `review_status: "unreviewed_candidate"`,
and the tool refuses to overwrite an existing output file so a partially-reviewed queue cannot be
silently replaced.

Running it against the current `sensor_data.db` (119,738 tracks, 6.1M observations) produced
**2,136 candidates from 662,499 eligible rows** (254,201 windows admitted a fit), with input-row
digest `5c228f7d93002334...` recorded in the frozen artefact for reproducibility.

## Finding: two distinct phenomena, not one

The candidate population does not represent one thing. The residual distribution has a sharp,
naturally-occurring gap: **nothing falls between 3.50 m and 6.52 m** in the actual data, splitting
2,136 candidates into 27 above the gap and 2,109 below it.

|               |     n | Residual range    | `peak_timestamp_ns` span            | Character                               |
| ------------- | ----: | ----------------- | ----------------------------------- | --------------------------------------- |
| Above the gap |    27 | 6.52 m – 129.78 m | 80 seconds, one window              | Confirmed defect, not a jump            |
| Below the gap | 2,109 | ≤ 3.50 m          | ~272 days, the full capture history | Consistent with genuine jump candidates |

**The upper tier is a storage-layer identity collision, not a tracker defect.** Direct inspection of
raw `lidar_track_observations` rows for 5 of the 27 (`track_169`, `track_160`, `track_31`, `track_42`,
`track_199`) shows the same `track_id` alternating — in the most severe cases every single frame —
between two or more spatially distant clusters (15 m to over 100 m apart) that each independently
trace a smooth, physically plausible trajectory. `track_199`, at the lowest severity in this tier
(6.52 m), shows a sustained version of the same pattern rather than an isolated excursion: two
independently smooth trajectories running in parallel roughly 15–20 m apart for the back half of the
window, not a single track with a brief anomaly.

**Root cause, confirmed.** All 27 excluded track IDs — and none of the 2,109 genuine
candidates — use the `track_<small integer>` format (`fmt.Sprintf("track_%d", t.NextTrackID)`), the
identifier scheme this deployment used before track IDs became UUIDs. That format is generated by a
per-process `NextTrackID` counter that starts at 1 every time a `Tracker` is constructed, which in
production happens exactly once, at server startup
([`radar.go`](../../../internal/cmd/server/radar.go)). Neither `lidar_tracks` nor
`lidar_track_observations` carries any instance, session, or restart-epoch column in its primary
key — only `track_id` (plus timestamp for observations) — so if the server process restarted (crash,
watchdog, redeploy) partway through a capture, the new process's counter started again from 1 and
silently aliased onto whichever earlier, still-recorded `track_id` it next reused. Nothing needs to
overlap in real time for this to happen: two non-overlapping tracker lifetimes writing into the same
unscoped table are sufficient, and a busy scene shortens the time to collision by burning through
track IDs faster.

This is not a live tracker bug: no single `Tracker` instance's gating or Hungarian assignment ever
associated a cluster 15–130 m away — each interleaved sub-trajectory is independently well-gated,
just recorded by a different process lifetime under a colliding ID. Confirming evidence:
inter-frame deltas across the alternating rows are all in the normal ~100–400 ms range (checked on
`track_31` and `track_199`), with no anomalous gap that would indicate covariance inflation or
runaway constant-velocity extrapolation. The defect was independently found and fixed by PR #276
(merged 2026-02-16, about ten weeks after this window), documented as item 1.1 in the
[garbage-tracks checklist](../troubleshooting/garbage-tracks-checklist.md#completed-p0p1-remediation):
`initTrack` now emits UUID-based IDs (`trk_<uuid>`), which cannot collide across restarts. This
production database's `sensor_data.db` capture predates that fix; every current build generates
collision-free IDs, so the defect cannot recur.

All 27 fall inside an 80-second window (`peak_timestamp_ns` 1764973030426104330 to
1764973110426054330). That is consistent with a single restart-triggered ID-collision episode during
a specific, likely crowded, scene — not a phenomenon spread across the deployment the way genuine
jump candidates are. It does **not** mean every candidate inside that time window is
suspect: `trk_b0449f37` (2.99 m, `peak_timestamp_ns` inside the same window) shows a fully smooth,
single-object trajectory with no alternation, consistent with an ordinary manoeuvre that happened to
occur during the same busy period. Severity, not timing, is what separates the two populations —
a busy scene plausibly produces both more genuine sharp manoeuvres and more association stress at
once, and the two remain distinguishable per-candidate.

**The lower tier matches the intended phenomenon.** Spot-checked at its boundary
(`trk_cd896035` at 3.50 m and `trk_e6f529b4` at 3.45 m, the two highest-severity candidates below
the gap): both show a brief single-frame excursion that recovers immediately to the surrounding
smooth trend, consistent with a genuine manoeuvre, measurement noise, or a transient association
error — an isolated anomaly in an otherwise continuous single-object trajectory, which is what a
jump candidate is supposed to be. This population spans nearly the entire multi-month capture
history, as a naturally-occurring driving-behaviour phenomenon should, in contrast to the upper
tier's 80-second concentration.

## Disposition

| Category                            |     n | `review_status` in the frozen artefact  |
| ----------------------------------- | ----: | --------------------------------------- |
| Excluded: confirmed distinct defect |    27 | `reviewed_excluded_distinct_phenomenon` |
| Frozen replacement set              |    33 | `reviewed_confirmed_candidate`          |
| Deferred pool                       | 2,076 | `reviewed_deferred`                     |

The **frozen replacement set** is the top 33 of the lower tier by severity (2.0 m to 3.5 m),
matching the scale of the unavailable historical set. This is the regression population: a future
estimator change should be measured against whether it reduces or preserves these residuals, the
way the original 33-track set was presumably used.

Full list, all fields, and every candidate's classification are in the frozen JSON artefact. The
**2,076-item deferred pool** is retained, not discarded: it is the broader analytically-screened
population below the defect threshold, available for a future, larger regression set, but not
individually point-cloud-verified beyond the boundary spot checks above — the threshold and its
boundary cases are what was reviewed, not every one of 2,109 candidates.

## What this closes, and what it does not

This closes the Phase 0 acceptance item "a reviewed, frozen replacement for the lost 33-track
regression set" (Section 21 Q8, and the Phase 0 acceptance criteria). It also closes the
80-second identity-mixing episode found as a side effect: root-caused above as a storage-layer
track-ID collision from the pre-UUID `track_%d` identifier scheme, already fixed by PR #276
(2026-02-16) before this investigation began, and structurally impossible in the current codebase.
No further action is needed.

Per-stage frame timing on a Raspberry Pi 4 remains a v0.6.x+ hardware-validation pass, not a
Phase 0 blocker: macOS M1, this plan's acceptance platform, already has published timings.

## Reproducing this review

```
python3 scripts/lidar-jump-candidates.py sensor_data.db --output /tmp/candidates.json
```

The extractor hashes its exact ordered input rows (`input_rows_sha256` in the output), so a
different `sensor_data.db` snapshot is immediately visible as a different digest rather than a
silent mismatch. The 5.0 m defect/genuine threshold and the top-33 selection are this review's
judgement calls, not the extractor's: reproducing the raw candidate list does not reproduce the
classification without repeating the review above.
